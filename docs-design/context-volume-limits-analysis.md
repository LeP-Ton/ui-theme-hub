# 上下文&体积限制方案分析

> 本文记录 ui-theme-hub 大小评估机制的设计决策与取舍依据。不是操作手册（操作见 [README「大小限制配置」](../README.md#大小限制配置)），而是回答"为什么这么做、为什么不那么做"。未来若要调整方案，先读本文。

## 一、要解决的核心问题

主题系统部署在 GitHub Pages，主题数量会持续增长。需要一个**编译期门禁**，防止主题无限膨胀。膨胀有两个维度，必须分开处理：

1. **上下文膨胀**：进 AI agent 上下文的文件（theme.json、patterns/*.tsx、standards/*.md）越来越大，挤占生成时的上下文预算。
2. **存储/传输膨胀**：编译产物（预览图、HTML、zip 包）越来越大，撑爆仓库和下载。

这两个维度的"大小"不是一回事，用同一个指标衡量会出错。

## 二、关键决策

### 决策 1：source 组用 token，output 组用字节

**结论**：进 AI 上下文的源文件按 token 量化；编译产物按字节量化。

**理由**：

| 组 | 量化维度 | 为什么 |
|----|---------|--------|
| source（进上下文） | token 数 | 这些文件被 AI agent 读取，token 才是真实的上下文消耗 |
| output（产物） | 字节数 | 图片/HTML/zip 是传输与存储成本，不进上下文。图片的 token 数没有物理意义 |

**为什么不统一用字节**：字节衡量的是"存储大小"，不是"上下文消耗"。两者没有稳定换算关系——同类文件 token 密度（字节/token）实测从 2.6 到 5.7 不等，差 2 倍多。统一用字节等于假设所有内容密度一致，这个假设不成立。

### 决策 2：token 计数用 cl100k_base 近似，不追求精确

**结论**：用 `gpt-tokenizer` 的 cl100k_base 分词器估算 token，明确标注为近似值。

**理由**：

1. **本系统面向通用 AI agent，不绑定特定模型**。GPT、Claude、DeepSeek、GLM 各用不同分词器，没有"正确的那个"。
2. **cl100k_base 是主流 BPE 分词器**，对各模型的 token 数都能给出合理的数量级估算。
3. **门禁目的是防膨胀，不是精确计费**。要拦的是"一个 tsx 膨胀到 5 万 token"这种失控，不是区分 2500 和 2800。数量级准确就够。
4. **性能与依赖成本**：cl100k 是纯 JS 实现，全量编码 22 个源文件仅 +25ms；加载多套分词器（DeepSeek/GLM 各自的 tokenizer.json）要多几十 MB 依赖，对一个防膨胀门禁太重。

### 决策 3：阈值按现状最大值留 1.7×~2.6× 余量设定

**结论**：每个阈值 = 现状最大值 × 1.7~2.6，确保现有主题全部通过，同时给未来留增长空间。

**理由**：门禁是防"失控膨胀"，不是卡当前正常迭代。留余量保证：① 现有主题不被误伤；② 正常的增长（比如 tokens 字段补充、pattern 加几个新组件）不会被门禁频繁打断；③ 真正失控的膨胀（数量级跳跃）能被拦下。

## 三、为什么不那么做（被否决的方案）

### 否决 A：全部用文件大小（字节）

**否决理由**：字节做代理会失真，且失真方向不可控。实测对比：

| 内容 | 字节 | cl100k token | 字节阈值(12KB)判定 | token 阈值(4000)判定 |
|------|------|-------------|------------------|---------------------|
| 重复内容（apple ×2500） | 15000 | 2501 | ❌ 超限（误拦） | ✅ 通过 |
| 真实代码（slide-deck.tsx） | 7245 | 2302 | ✅ 通过 | ✅ 通过 |

- **误伤**：重复内容对 AI 来说只有 2501 token（分词器对重复模式压缩极狠），完全在预算内，但字节阈值会拦下。AI 生成的模板里出现重复 className、相似结构很常见，字节会频繁误报。
- **漏放**：高信息密度内容（密集中文、紧凑代码）字节不多但 token 很高，字节阈值放过了，上下文却吃紧。

**核心比喻**：字节是"精确的体重秤"，token 是"略有误差的体温计"。防"发烧"（上下文膨胀）该用体温计，哪怕误差 ±0.3℃——而不是用体重秤，因为体重和发烧不是一回事。字节"确定地衡量了错误的东西"。

### 否决 B：加载多套分词器分别计数（DeepSeek/GLM 各算一次取 max）

**否决理由**：

1. **依赖与运行时成本高**：要加载各模型的 tokenizer.json，多几十 MB，构建变重。
2. **违背门禁轻量初衷**：防膨胀门禁应该简单可靠，不该为了 ±25% 的精度引入复杂依赖。
3. **收益有限**：阈值已留 1.7×~2.6× 余量，25% 的偏差在余量内，不会导致漏放失控文件。

### 否决 C：按某模型实际分词器精确计数

**否决理由**：本系统面向通用 agent，绑定任何单一模型（哪怕精确）都违背通用性。而且 Claude 等模型的分词器未开源，根本无法精确。近似 + 余量是通用场景下的正确姿态。

## 四、已知局限与可接受性

### 局限 1：cl100k 对非 GPT 模型有偏差

- 中文内容上，DeepSeek/GLM 实际 token 数通常比 cl100k 估算高 10-25%（GLM 偏少、DeepSeek 偏多、Llama3 偏多更明显）。
- **可接受**：阈值留了 1.7×~2.6× 余量，25% 偏差在余量内。且偏差方向有利——非 GPT 模型实际 token 更多，意味着 cl100k 算着通过的文件实际可能更大，门禁对它们其实更宽松（不会漏放失控文件，临界情况有 10-25% 灰区）。

### 局限 2：临界情况有灰区

- 一个文件 cl100k 算 3800 token（低于 4000 阈值通过），DeepSeek 可能实际 4750 token（超阈值）。
- **可接受**：门禁防的是数量级膨胀，不是临界精度。灰区文件离失控很远，没必要为它牺牲方案简洁性。
- **如需更保守**：可将 source 阈值再收紧 20% 给非 GPT 模型留缓冲，但会让余量从 1.7× 降到 ~1.4×，可能误伤正常主题。当前选择不收紧。

### 局限 3：token 密度极端内容

- 极端重复内容（token 极少但字节大）会被 token 阈值放过，但这类内容存储成本由 output 组的字节阈值兜底（若它进了 zip）。
- 极端高密度内容（token 多但字节小）会被 token 阈值正确拦下——这正是 token 量化的优势。

### 局限 4：单主题物理总量的覆盖范围

"单主题总大小"由两层限制覆盖，但都不完整：

- **源文件 token 总量**（`themeContextTotal` 15000 tokens）：卡 theme.json + tsx + md 的上下文成本。
- **zip 下载包总量**（`themeZip` 2MB）：卡 theme.json + patterns + standards + assets 的压缩后下载体积，与 `assetFile` 512KB 协调（单文件防失控、总量防数量累积）。
- **未覆盖：previews 目录**。zip 打包时排除了 previews（下载后不需要），所以预览图膨胀只由单文件 `previewImage` 4MB 卡，没有"单主题预览图总量"约束。这是有意设计——previews 不进下载包、不进上下文，只影响仓库体量，由单文件阈值兜底即可。

## 五、方案通用性声明

本方案不绑定任何特定 AI 模型：

- **机制层**（fail build、violations 收集、阈值配置）：纯 Node.js，与模型无关。
- **token 计数层**：cl100k_base 是通用 BPE 分词器，对各模型给出数量级估算。
- **消费链路**：summary 远程读 + zip 下载按需读源文件，是通用资产分发模式，任何 agent 都能消费。

任何 AI agent（GPT、Claude、DeepSeek、GLM、Llama 等）都可以消费这套主题系统，大小门禁对所有模型都生效，只是 token 数为 cl100k 近似值。

## 六、决策回顾点

未来若出现以下情况，重新审视本方案：

1. **主题数量接近 summary 阈值天花板**（约 65 个主题）→ 考虑分层索引或拆分仓库，而非单纯调阈值。
2. **非 GPT 模型成为主要消费方且临界精度成问题** → 考虑收紧阈值或引入多分词器。
3. **assets 物料（插画/图标）开始大量使用** → 当前 assetFile 512KB 阈值可能需调整，或引入图片压缩管线。
4. **pattern-preview HTML 的 antd 内联问题被根治** → output.patternPreviewHtml 阈值可大幅下调。
